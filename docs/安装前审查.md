## 仍然存在的已知限制（诚实说明）

1. **导入前不自动备份整个 `~/.dsh`**。台账只记录"导了什么"，不是完整快照。要更强保险需手动备份 `sessions` + `session_projcache`。
2. **`close` 失败后写租约可能未释放**。已降级为警告，但可能需重启 DSH 清理。
3. **thinking 降级**：用非原模型续聊时 DSH 会把历史 thinking 当正文重放，属 DSH 自身行为。
4. **回滚只删文件目录，不动索引**；索引在 DSH 重启后自动重建。
5. **所有工具调用挂在 `step=1`**：结构性简化，不影响 v4 校验，但续聊时的 step 展示可能与原生会话不同。
6. **插件安装后需重启 DSH 才加载**；本次按要求只安装、不运行。

### 宿主 Relationships 的真实铁律（此前全部违反）

1. 	ool/call 的 callId 必须先出现在某条 ssistant/message 的 	ool-call 块里
   （line 642: has no advertised tool lifecycle）——插件从未在 assistant 消息里放块

3. step/end / 	urn/end 时 tools 表必须为空（line 577: leaves unresolved tool call）
4. 同一 callId 只能广告一次（line 630）、只能有一个 result（line 648 delete 后即无）
5. session/title（fallback 来源）必须用 messageSeqs 引用更早的 kind=user 的
   user/message（line 838）——插件发的是空引用
6. WorkBuddy 数据的三个脏模式：result 行先于 call 行落盘；user 记录插在 call/result
   之间；同一调用写多行重复记录

### 修复

- uildEvents 重写为严格三连：广告 assistant → tool/call → tool/result

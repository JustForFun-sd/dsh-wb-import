# 会话格式修复记录（2026-11-07 ~ 11-08）

这份记录是这轮把 WorkBuddy 会话导入 DSH 时，**逐个踩出来的格式坑**。
每个坑都是"导入看起来成功、但会话打不开或内容不对"，根因都在**生成的会话事件缺字段/结构不对**。

---

## 一、格式坑清单（按踩坑顺序）

### 1. `assistant/message` 缺 `message.id`

**报错**：`session event at seq 6 lacks an identified message`

宿主要求每条 message 有 first-class `id`。`user/message` 和 `tool/result` 都带了，只有 assistant 漏了。
**修**：三处 assistant message 都补 `id: randomUUID()`。

---

### 2. `assistant/message` 的 source 缺 `provider` / `model`

**报错**：`session event at seq 6 message must have model source`

宿主 `hasProviderModel()` 要求：
```js
{ kind: 'model', provider: '<非空字符串>', model: '<非空字符串>' }
```
只写 `{kind:'model'}` 不合格。
**修**：从 WorkBuddy 每条记录的 `providerData.model` 取真实模型名（如 `hy3`、`hy4-preview`），会话级取第一个作 fallback。

---

### 3. `assistant/message` 缺 `stream`

**报错**：`seed assistant/message at index 6 has invalid settlement fields`

宿主 `assertAssistantSettlementShape()` 要求：
```js
turn 是非负安全整数
step 是非负安全整数
data.stream 必须是数组     ← 漏了这个
```
`stream` 是流式渲染记录，**空数组合法**（内容不校验）。
**修**：三处 assistant message 都补 `stream: []`。

---

### 4. `turn/end` 缺 `reason` —— 前端崩溃

**现象**：会话打不开，只显示"加载更早"；控制台报
`TypeError: Cannot read properties of undefined (reading 'kind')`

前端 `endFailure()` 直接读 `reason.kind`，**没有任何 undefined 保护**：
```js
function endFailure(reason) {
  switch (reason.kind) {              // ← reason 是 undefined 就崩
    case "aborted": return reason.reason.kind === "hook" && ...
```
`dsh-client-ui-chat` 里有 6 处这样裸读 `data.reason.kind`。
**修**：所有 `turn/end` 补 `reason: { kind: 'completed' }`。

---

### 5. **step 粒度错误** —— 每轮只开一个 step

**现象**：同样打不开，前端渲染失败。

DSH 的对话是**按 step 组织**的。本机会话每轮有几十上百个 step：

```
step/start step=1
  assistant/message step=1
  tool/call step=1
  tool/result step=1
step/end step=1
step/start step=2
  ...
```

实测对比：

| | 每轮 step 数 |
|---|---|
| 本机会话 | 196、95、123 |
| 错误产物 | **1**（整轮塞一个 step） |

**修**：`ensureStep`（复用同一 step）→ `beginStep`（每次 assistant 消息/工具调用都开新 step，用完 `step/end`）。

---

### 6. 会话没挂进工作区 —— 显示在"未分组"

**根因**：DSH 只在**启动时**（`bootstrap()`）按 cwd 自动分组：
```js
const sessionIds = group.headers.map(h => h.id)
  .filter(sessionId => !accounted.has(sessionId));
```
导入发生在启动之后，所以从没被 bootstrap 处理过。
**修**：导入后显式调 `workspaceRegistry.resolveByPath(cwd)` → `entity.attachSession(dshId)`；回滚时 `detachSession`。

---

### 7. 侧边栏标题显示"未命名"

**根因**：DSH 侧边栏标题读的是**投影缓存**（`~/.dsh/storages/session_projcache/sessions/<id>.json`），**不是**会话日志里的 `session/title` 事件。缓存只在会话被打开过一次时才由宿主生成。

**修**：导入时同步写一份缓存：
```json
{ "version": 7,
  "record": {
    "identity": { "formatVersion": 4, "createdAt": …, "cwd": …, "isSeeded": false, "inheritedEventCount": 0 },
    "rows": { "title": { "ver": 1, "seq": <title事件seq>, "val": "<标题>" } }
  } }
```
`identity` 必须与 header 精确匹配，否则宿主判为不匹配直接忽略（**不会损坏**，只是标题不显示）。
回滚时同步删缓存条目。

---

### 8. 标题和原会话不一致

**根因**：WorkBuddy 文件里有**多条 `ai-title`**（会话进行中会改写标题）。
取最后一条 → 拿到中途改过的标题。
**修**：取**第一条**（原始标题）。

---

### 9. 系统注入内容被当成用户发言 —— 内容错

**现象**：对话里冒出大量"用户输入"，其实是上下文/通知。

WorkBuddy 会把几类系统注入塞进 `role=user` 的记录：

| 类型 | 说明 |
|---|---|
| `<conversation_history_summary>…</conversation_history_summary>` | 上下文压缩摘要 |
| 摘要残片（只有闭合标签，无开标签） | 几千字正文，最容易漏 |
| `<task-notification>…</task-notification>` | 后台任务完成/失败通知 |
| `Use the TaskOutput tool with task_id=…` | 任务通知剥完后的尾部指令 |
| `Please continue with the conversation based on the summarized context…` | 压缩后的续接指令 |
| `<system-reminder>` / `<cb_summary>` | 提示块 |

**修**：两层过滤
- `extractRealInput()` —— 剥注入块，剥完若是纯续接指令则丢弃
- `buildEvents()` 里 `isInjectedUserText()` —— 二次兜底

实测：`178 → 110` 条用户消息，最长 207 字（之前有 7726 字的假发言）。

---

### 10. 导入慢（30-45 秒）

**根因**：宿主每次 `handle.append()` 都要 **fsync 落盘**。
批次设成 1（每行一帧）→ 15591 次 fsync → 30 秒以上。

耗时剖析：
```
fsync      2660ms  ← 74%
zstd 压缩   312ms
其它        607ms
```

**修**：`APPEND_BATCH_EVENTS = 20`（实测最佳平衡）

| 批次 | 帧数 | 文件 | 压缩 | 全量读取 |
|---|---|---|---|---|
| 1 | 15591 | 13.6MB | 510ms | 219ms |
| 10 | 1533 | 10.0MB | 197ms | 58ms |
| **20** | **767** | **9.2MB** | **198ms** | **47ms** |
| 50 | 307 | 8.1MB | 207ms | 42ms |

效果：`3579ms → 2073ms`（快 42%），文件还更小、读取更快。

---

## 二、根因总结

宿主有两套校验：
1. **加载校验**（`assertMessageEventShape` / `assertAssistantSettlementShape`）——不合格会报 corrupt
2. **前端渲染**（`dsh-client-ui-chat` 等）——**读字段不做 undefined 保护**

所以"宿主校验通过"**不等于**"前端能渲染"。前端要求的字段比宿主校验器更多。

---

## 三、校验器覆盖范围（`wb-diag/lifecycle-validator.mjs`）

复刻了宿主的完整规则，并加了**反向测试**（构造错误输入，确认能抓出来）：

| 检查项 | 对应坑 |
|---|---|
| message.id 非空 | 坑 1 |
| role 与事件类型匹配 | 坑 1 |
| content 是数组 | 坑 1 |
| assistant source 含 provider+model | 坑 2 |
| tool source 含 callId 且与 toolCallId 一致 | — |
| turn/step 安全整数 + stream 是数组 | 坑 3 |
| turn/end 必须有 reason | 坑 4 |
| 工具三连生命周期（advertise → call → result） | 早期坑 |
| seq 稠密、surfaceOp=append | 早期坑 |

`test-validator-negative.mjs`：8 个断言，能复现 4 种 bug。

---

## 四、教训

1. **"导入成功" ≠ "能用"**。导入工具报成功，只是文件写下去了；能不能打开、内容对不对，要另外验。
2. **校验器覆盖不全 → 假阳性通过**。这轮踩了 4 次同样的坑：每次补一层校验，就发现前面还漏一层。
3. **改完必须同步安装副本再测**。有两次测试实际跑的是旧代码。
4. **不要瞎补字段**。有一次我给 `usage`/`meta` 乱补字段，方向错了——本机会话正常说明 DSH 没问题，该查的是**结构差异**（step 粒度），不是给 DSH 加字段。
5. **对照本机会话是最有效的方法**。逐事件对比字段、对比 step 结构，比读源码猜快得多。
